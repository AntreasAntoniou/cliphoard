# Security boundary and production IPC gate

The standalone Windows UI now runs entirely in the interactive user process, with bounded real clipboard capture and current-user DPAPI history. It has no engine/service IPC. The Rust foundation still implements bounded protocol/domain behavior and an explicitly opted-in synthetic child-stdio transport. It does **not** implement the selected production service IPC. `cliphoard-engine` with no flag or `--windows-service` refuses78 before reading input. The separate WinUI test harness requires exactly `--synthetic-fixture`; it creates its fixed adjacent engine binary as a non-shell child with redirected handles. Its generated/marked fixture content is not a safe basis for production IPC claims.

Before enabling a Windows per-user service, implement and qualify all of:

1. Derive the current token user SID and logon/session identity from Windows, never a request field. Create a local named pipe with a protected explicit DACL granting only the selected current-user SID required access. Do not rely on default DACL, Everyone, authenticated-users or an owner string supplied by a client.
2. Set `FILE_FLAG_FIRST_PIPE_INSTANCE`, a single instance policy and `PIPE_REJECT_REMOTE_CLIENTS`. Reject pipe squatting, second creators and UNC/remote access. Scope a deterministic pipe name to the OS-derived user and session; do not accept an arbitrary path from a request.
3. After connection and **before parsing any content payload**, establish client OS identity using the supported native process/token and pipe peer APIs. Compare user SID, session/logon context and the connected process; fail closed when it cannot be established. If using impersonation, use the OS-authenticated pipe client context, bound it and always revert. No JSON SID or self-declared PID is an authentication mechanism.
4. Before the frontend sends any payload, get the named pipe server PID/session, open and validate its current process token owner/session, retain process identity and establish the expected engine executable/deployment ownership. A matching pipe name or claimed hello packet is insufficient. Test the legitimate service and an attacker-created pipe under a different identity/session/PID.
5. Use bounded overlapped I/O, deadlines, cancellation and one-flight processing. Reject malformed/truncated/over-limit frames before allocating or dispatching. Enforce lifecycle/lock at dispatch and after asynchronous boundaries. No generic command, file path or SQL operation may be added.
6. Independently qualify x64 and ARM64 with positive and negative local identity/ACL/remote/squatting tests. Until these pass, keep the production gate closed. Cross-compilation is not native qualification.

The fixture clipboard listener checks only the registered marker format until it matches a private per-run value. It reads bounded Unicode text only after that match and requires the synthetic prefix. This fixture path has no real capture, previous clipboard backup, private history/keychain/model import or personal data fixture. The marker is a privacy fixture gate, not a production authentication primitive.

Paste target capture retains a queried process handle and records its window/PID. It checks the target token's user SID, current session, process liveness and current window/PID; restores foreground normally, then requires that exact target to remain foreground before one input submission. It refuses held modifiers and never forces activation with thread attachment or elevated access. SendInput can fail under UIPI; any failed/short submission leaves synthetic text copied for manual paste. An input-count receipt is not proof the receiving app accepted text. Native race/focus/UIPI qualifications are recorded in the 14 November input reports; the normal UI reuses that guarded target/input implementation.

Lock drops UI rows and volatile engine entries, blocks future fixture capture/search/select and disposes target identity. Rust allocator/JSON/string copies are not guaranteed zeroized. That fixture admits no personal clipboard content. The separate interactive application below implements real capture and encrypted persistence; crash-dump hardening and secure managed-memory erasure are not claimed.

## Standalone interactive application

Normal launch keeps clipboard handling and history in the interactive user process. It has no TCP listener, named pipe, service or elevation. Optional Gemma inference uses the owned private model worker described below. Its singleton mutex/reopen event use .NET `NamedWaitHandleOptions` with both current-user and current-session restrictions. The event carries no content or commands beyond showing the bar. Invalid command-line modes still refuse78; Rust ordinary/service invocation still refuses78.

Capture baselines the existing clipboard sequence at startup/resume, and reads future updates only. It respects `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory=0`, and concealed content. Pause does not backfill copies when resumed. Real clipboard contents are never written to diagnostic logs. Text is limited to 65,536 UTF-16 characters, rich text to 512 KiB, file lists to 32 paths without reading the referenced files, and 24/32-bit uncompressed/bitfield DIB images to 8 MiB and 8192 pixels per dimension. External image profiles are refused. Unsupported/oversized formats are skipped. Replayed clips opt out of Windows clipboard history/cloud upload; own writes are sequence-suppressed after CloseClipboard.

History at `%LOCALAPPDATA%\Cliphoard\history.dpapi` is DPAPI current-user ciphertext, atomically replaced with no plaintext sidecars. The app directory has protected user+SYSTEM access. Reparse-point app directories/history files are refused. History defaults to 200 entries, supports 50–500, and trims unpinned entries to a 24 MiB content budget. Pins are bounded to 20 entries/8 MiB. DPAPI failure preserves the saved file and switches that run to memory-only operation. This is protection at rest, not protection from processes already running as the owner. No secure managed-string erasure or crash-dump exclusion is claimed.

Session lock/disconnect invalidates the paste epoch, drops targets, stops capture, hides the UI and releases history/UI references. Reconnect/unlock reloads encrypted history and baselines future capture; it does not show the panel automatically. This differs deliberately from the synthetic harness's permanent-until-restart lock. Paste still requires the retained exact process/window stamp, same SID/session, normal foreground restoration, no held modifiers, and the qualified one-attempt SendInput backend. A partial input return still disables automatic input for that run.

Appearance, layout and preview-height preferences share the encrypted history envelope; unknown values fall back to supported defaults. Returning from Settings or Inspect preserves the captured original target rather than capturing whatever window Windows foregrounds on auxiliary close. Quick-paste modifier release is bounded to 28 waits of 15 ms, with target/epoch admission rechecked after every await and before clipboard mutation. File open/reveal are explicit gestures only, restricted to fully qualified local drive paths; capture remains free of file-content reads and launch side effects.

## Windows feature follow-up

Real capture now also respects transient/auto-generated formats and configured process-name exclusions, using the clipboard owner's OS process where available. Known password-manager processes are excluded before content payloads are read. PNG-only payloads use a stable persisted sentinel mapped back to the runtime registered PNG format. Bounded CF_HTML is retained without active rendering. User tags and exclusions remain inside the DPAPI envelope.

The optional launch-at-login toggle only owns `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Cliphoard.Windows`. It refuses to replace a different installation's value, removes only its exact command, and uses `--background` to avoid summoning on login. Tests do not enable it silently.

Shared `.cliphoard` exports use the shipping Mac CLIPHRD1 v1 authenticated chunk/record format. Readers enforce the bounded KDF work factor, header, summary, AAD, record counts, hashes and authenticated final boundary before merging. Writers use fresh salt/nonce prefixes, PBKDF2-SHA256 with 600,000 rounds, HKDF expansion and AES-256-GCM. NFC passphrases require at least 12 grapheme clusters. Legacy `.cliphoard-win` imports retain their existing authenticated format and rune-based passphrase compatibility. Archive imports are bounded to 48 MiB and retain the Windows history, image and pin limits. Capture pauses through picking, passphrases and confirmation. Closing or locking prevents final publication/application. Ciphertext is atomically written. The native Save picker may leave an empty newly selected file if the passphrase dialog is cancelled.

Semantic acquisition starts only through an explicit download action and uses immutable Hugging Face revision/SHA-256/size pins. Verified model bytes are loaded directly into the CPU runtime. Clipboard content stays local. Cached vectors remain in memory and clear on session revocation. Exact search remains available when inference cannot load. OCR uses installed Windows languages with bounded decoding/scaling. Recognized text stays in the DPAPI history envelope. Model weights are excluded from release payloads.

Protected imported flags and locally detected high-confidence private-key/vendor-token/JWT signatures veto semantic analysis and OCR. Protected preview text, source and tags are concealed. Explicit reveal requires Windows Hello, with unavailable/failed verification refusing reveal. Reveal grants clear on dismissal or session revocation. Capture baselines around verification. The Windows detector currently implements a subset of the Mac detector suite. Successful Hello verification still needs owner-device qualification.

Per-user MSI uninstall removes only the exact owned startup command and installed payload. History and downloaded model caches remain in their separate user-data directory. Release packaging retains compiled WinUI resources and license notices. ZIP/MSI/MSIX artifacts are unsigned private builds. MSIX installation awaits a trusted publisher signing workflow.

## Model-family expansion — 16 November 2026

All model assets use immutable origin revisions, exact sizes and SHA-256 pins. Atomic downloads refuse reparse-point ancestors and verified readers retain file leases. Weight-free executable ONNX graphs are compiled resources. OpenVision checkpoint ZIP storage is read as bounded tensor data using compiled names, shapes, strides and offsets. The app never executes Python or deserializes pickle instructions from a downloaded checkpoint.

EmbeddingGemma uses the official Windows x64 LiteRT-LM CPU runtime through a private adjacent worker, including system emulation on Windows ARM64. The worker has a bounded length-prefixed anonymous stdio protocol and no listener. Windows job ownership terminates the worker on frontend death. Session/model lifetime cancellation terminates it immediately. Superseded ordinary queries finish their bounded response and discard the canceled result, retaining a usable worker. Process identity uses retained kernel handles. Downloaded runtime and model bytes remain verified and read-leased during use.

Image indexing respects protected-content vetoes and clears vectors on session revocation. Speech starts only from the explicit inspector action on a fully qualified local WAV path. The parser enforces PCM16 mono 16 kHz, ten minutes and a 20 MB input bound. The source is read-leased, decoded buffers are cleared, and closing the inspector, model changes or session revocation cancel processing. Transcript text is scanned before indexing and persists only inside encrypted history. Managed strings retain the existing memory-erasure limitations. Gemma audio embedding inputs are separately bounded to thirty seconds.
