# Disabled approved-envelope persistence and recovery

This candidate adds exactly two source files, their two focused test files and this note. All Swift declarations remain inside `CLIPHOARD_DEVICE_LICENSING_PROTOTYPE`. There are no shipping callers, defaults, production paths, trust keys, settings, manifests, dependency changes or startup work. Existing CLIP1 and StoreKit behavior is untouched. The selected policy remains one purchaser's personal Macs, email approval per new device, no fixed device cap and indefinite offline approval. No burst threshold, software-key fallback, issuer rotation or account-transfer policy is selected.

## Interfaces and trust

`DeviceLicenceReceiptRepository` takes an explicit file URL. Its constructor performs no I/O. Its asynchronous `read` returns an **unverified** envelope and opaque revision; `replace` is a storage primitive, not an authorization API. The trusted integration boundary is `DeviceLicenceRecovery`: inject the repository, a `DeviceIdentity` configured with chosen adapters, and immutable bindings containing the exact issuer key ID/public key, device public key and entitlement ID. No stored field adds an issuer key or changes those caller-supplied bindings. Production custody and sourcing of these public binding pins remains unimplemented.

`restore()` reads the envelope, calls only `loadExisting()` on the identity, and uses the existing verifier to authenticate the exact signature, strict CLIPD1 protocol and a fresh receipt-bound device-possession proof. It then compares the verified entitlement, issuer and device hash to the pins. No raw receipt fields are rehydrated as trusted state. A new coordinator starts without a published receipt. Missing or unusable identity returns a recoverable error, never implicit key creation, deletion or fallback.

`accept(envelope)` first reads and authenticates any existing envelope, then authenticates the new envelope before replacement. Unknown/corrupt previous bytes therefore cannot be silently repaired or overwritten by import. An exact duplicate performs fresh verification but does not rewrite the stored record. Successful replacement must return the exact envelope and a revision before the coordinator publishes the already verified receipt. A failure preserves its previous verified in-memory receipt and records only a typed failure. A later explicit restore can recover a successfully committed record after an uncertain acknowledgment.

The value reducer remains unchanged. This coordinator does not issue activation requests, make network calls, check a clock, observe refunds/holds or convert a receipt into the shipping application's entitlement. An old approved receipt has no expiry or remote revocation. New approvals and their entitlement/admission rules remain the service's responsibility.

## Exact storage format and path boundary

The file is ASCII: `cliphoard.approved-envelope\n1\n`, a canonical lowercase UUID generation, one LF, then the **exact** CLIPD1 envelope with no trailing LF. The container rejects unknown versions, extra fields, noncanonical UUIDs, invalid envelope framing and oversized input before unbounded parsing. Reads are capped at 1200 bytes and the enclosed envelope at the verifier's 1024 bytes. Signature and nested payload semantics are checked by the recovery verifier, not by the storage primitive. CAS revisions are SHA-256 of the whole stored record, including the fresh generation; successful rewrites do not recreate an earlier revision merely because the envelope repeats. No private keys or email addresses are stored.

The caller must supply an existing private directory on a local filesystem, using a physical absolute path. Every path component is opened descriptor-relatively with `O_NOFOLLOW`; symlink aliases such as `/tmp` must be resolved deliberately by the caller before construction. Ancestors must be owned by root or the current user and have no group/other write bits, except root-owned sticky directories. The final directory must belong to the current user, have no group/other permission bits, and have no extended ACL entries. Existing receipt/lock files must be regular, single-link, current-user-owned files without group/other permissions or extended ACL entries. FIFO, directory, symlink and hardlink targets fail closed. Constructors and operations never create a parent directory, chmod an existing object, remove an ACL, repair a path or follow an alternate location.

Extended ACL absence on the tested macOS returns `NULL` with `ENOENT` from `acl_get_fd_np` on a valid open descriptor. This is accepted as absent; all other ACL errors fail closed, and an allocated ACL must have no entries. The focused evidence records that characterization and rejection of an explicit ACL on a newly created test fixture. A second characterization found that Foundation's `resolvingSymlinksInPath` retains the `/var` alias here; the fixture uses POSIX `realpath` to obtain its physical temporary parent, without relaxing the repository. Ancestor ACL policy, filesystem/cloud-provider qualification and signed-app sandbox access require integration review. These checks are not a security boundary against root, compromised same-user code or a client patcher.

## Atomic replacement, concurrency and cancellation

A utility queue runs blocking filesystem calls away from the main actor. Each operation opens the persistent sibling `.<filename>.lock`; if absent, it attempts exclusive creation, and a competing creator produces `busy`. It then requests an exclusive **nonblocking** `flock`; contention also returns `busy`, without polling or automatic retry. The lock is never removed. Under that lock, replacement reads and validates the current record and compares its revision with the caller's expected revision. It writes a fresh same-directory exclusive temporary file with mode 0600, requests `F_FULLFSYNC` on that file, then claims the operation's cancellation permit immediately before `renameat`. After rename it requests directory `fsync` and reads back the record while still holding the lock.

This CAS domain includes cooperating repository instances/processes opening the same stable lock inode on a local filesystem. It does not rely on an actor for cross-process exclusion. It does not cover unrelated writers that ignore/unlink the lock, remote volumes, cloud synchronization, malicious rollback or replacement of the containing directory. Independent-instance tests exercise the OS lock through separate descriptors; an actual multiprocess/crash/power-loss test is not claimed.

The permit claim is the cancellation/commit linearization boundary. Each new coordinator request invalidates the prior permit before awaiting; all asynchronous returns are fenced by a generation ticket. Cancellation observed before the claim prevents rename, even if a storage adapter was delayed after verification. A claim already won cannot be undone by a later cancellation. The late result may be discarded by the coordinator, but valid committed bytes are never rolled back. Task cancellation follows the same permit path. There is no hard deadline for an OS I/O call already running on the utility queue.

Known read/write/file-sync failures before the claim leave the old destination untouched. Any error during rename or subsequent directory sync/readback is `commitUncertain`: the new record may already exist, and the implementation never restores old bytes or retries automatically. Its own unrenamed temporary file is cleaned up on normal failure; process termination can leave a private temporary file, which is not interpreted as an approved receipt or automatically deleted later. Corrupt original bytes remain in place. There is no backup archive, corruption reconstruction or guarantee against disk loss.

Atomic visibility and requested synchronization are separate from demonstrated durability. No claim is made that the drive, filesystem, directory sync or hardware survives power loss correctly. Unsupported synchronization fails closed before rename where possible and reports uncertainty after rename. Apple explicitly distinguishes `fsync` from device-cache flushing; use of `F_FULLFSYNC` here is a requested stronger flush, not a measured hardware guarantee.

## Focused evidence and remaining work

Tests use new temporary directories only, synthetic P-256 keys kept in memory and fake identity storage/key operations. Native Secure Enclave/Keychain adapters are never instantiated. They exercise recreation with fresh proof; exact bindings; invalid/cross-device/cross-issuer imports; duplicate handling; missing identity and hardware/read outages; malformed/oversized/semantically corrupt records; symlink/hardlink/ACL/private-directory rejection; independent-instance CAS and separate-descriptor contention; partial writes and sync faults; accepted-before-acknowledgment uncertainty; delayed stale commits; and cancellation before/after commit. Relaunch means coordinator recreation against retained files/fake hardware, not an actual app launch or hardware reboot.

The focused command is `swift test --jobs 2 --disable-automatic-resolution --skip-update -Xswiftc -DCLIPHOARD_DEVICE_LICENSING_PROTOTYPE --filter 'DeviceLicence(Recovery|ReceiptRepository)Tests'`. All 24 focused cases pass on Swift 6.4 after the recorded corrections. The final source also typechecks with the prototype flag absent in both default and APP_STORE configurations. Only these new test classes run; existing tests may compile with existing warnings. The initial failing test run, compile correction, absent-ACL and Foundation-path characterizations/failures, first-lock creation race and correction, subsequent focused logs, exact five-file patch and hashes, and before/after inventory of all 381 tracked baseline files are retained in `.delivery/`. Temporary diagnostic error instrumentation used to locate the lock-open failure is removed from the candidate. No existing baseline test suite is rerun.
