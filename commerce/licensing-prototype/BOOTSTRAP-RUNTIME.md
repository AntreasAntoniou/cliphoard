# Disabled bootstrap custody and shared alarms

These two adapters are additions only. They have no shipping caller, Worker export, environment access, credential import/generation/export, provider binding or production policy default. Both require an own data `enabled: true` switch. Construction is inert; enabled dependencies are captured as exact own-data properties. Malicious Proxy traps and malicious trusted callbacks are outside this capture boundary.

## Custody

`createDeviceBootstrapSealer({ enabled, keyID, key })` returns `seal(plaintext, context)` and `open(envelope, context)`. The host supplies a separate, nonextractable AES-GCM 256-bit `CryptoKey` with exactly encrypt/decrypt usages. The adapter neither obtains nor persists that key. Production custody, backup, restoration and rotation remain host obligations; nonextractable WebCrypto handles do not prove hardware custody or a protected provider key-management service.

The bounded string format is `CLIPBS1.<keyID>.<canonical-base64url-IV>.<canonical-base64url-ciphertext>`. Each seal uses a fresh random 96-bit IV and a 128-bit authentication tag. Authenticated context is the fixed bootstrap-custody purpose/version, captured key ID and exact caller-supplied scope/purpose string. Plaintext and context are nonempty, losslessly UTF-8 encoded strings of at most 2,048 bytes. Callers must provide context that independently binds the purchase, entitlement, record purpose and immutable selected pins. The whole handle-bearing CLIPB1 envelope must be sealed; encrypting only a separate handle column is insufficient.

Opening rejects a wrong purpose/key ID, noncanonical encoding, oversized text, damaged ciphertext, wrong key or different context. It does not rotate a key, regenerate a handle or fall back to cleartext. This is authenticated encryption, not anti-rollback: an old valid ciphertext for the same context still decrypts, so the durable service must own revisions and terminal state. Strings and provider internals are not physically zeroized.

## One physical alarm, two logical channels

`createDeviceLicenceAlarmMultiplexer({ enabled, storage, physicalAlarm, clockMilliseconds, recoveryDelayMilliseconds, handlers })` returns `{ activation, bootstrap, alarm, recover }`. `storage` is the existing SQL/transactionSync/sync shape; `physicalAlarm` is the platform's getAlarm/setAlarm/deleteAlarm/sync capability. `handlers` has exactly `activation` and `bootstrap` zero-argument callbacks. The explicitly supplied positive recovery delay is bounded to one day; no production value is selected.

Each channel has the existing getAlarm/setAlarm/deleteAlarm/sync interface. Two small SQL tables retain logical schedules and dispatch guards. Updating one channel reconciles the physical alarm to the earliest retained schedule/guard; deleting one channel cannot delete another's wake. A new logical schedule first durably arms a physical fallback, then writes and synchronizes its SQL schedule. Recreated recovery uses retained SQL without invoking either handler.

`alarm()` first restores a physical fallback, advances due logical schedules and writes durable per-channel dispatch guards, synchronizes, then calls due handlers outside the short serialized wake queue. Due activation and bootstrap handlers can progress independently. A handler must reconcile its own logical schedule through its channel. A guard remains while that callback is unsettled, even if it deletes its logical schedule. Later alarm entry rearms guards and does not invoke an already-running handler again. Success removes only that dispatch guard; failure retains a recovery guard and throws a sanitized dispatch error. A recreated owner can run work left guarded after interruption. No hard timeout/preemption of trusted handler, SQL or platform I/O is claimed.

The host must construct **one** multiplexer per live Durable Object instance and pass only its logical channels to both runners. Concurrent independently constructed multiplexers driving the same physical alarm are unsupported. Recreate it only when the old object is no longer running. Existing direct physical-alarm wiring must not coexist with it. Native callback success, platform alarm execution and actual email inbox delivery are separate observations. These adapters neither authorize purchases nor revoke receipts.

The focused local Node 24.11.0 suite covers authenticated sealing/substitution/tampering/bounds/capture, independent channel deletion, same-database scheduler recreation, simultaneous due handlers, consumed wakes behind unsettled work, failure after logical deletion and failed prearm. The initial absent-module import failure is retained; it ran no behavioral assertions. Synthetic ephemeral keys exist only in process memory. Local in-memory SQLite and fake physical alarms are not a deployed Durable Object or power-loss durability test. The integrated real local workerd observation is separate evidence.
